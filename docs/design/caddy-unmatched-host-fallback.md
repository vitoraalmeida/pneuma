# Design - Caddy Unmatched-Host Fallback

**Status:** approved design for v0.4 checkpoint 1.

**Base:** `6ccd178` (`chore: remove redundant VPS validation scripts`)

## Objective

Return a generic HTTP `404 Not Found` for requests that reach Caddy without a
matching public Application route. When an Application becomes `internal`, its
managed Caddy fragment continues to be removed; the generic fallback handles a
subsequent unmatched HTTP request.

## Scope

- Add the fallback to the canonical Caddy baseline generated by
  `scripts/lib/provision-host.sh` for production and VM local-certificate modes.
- Preserve public Application fragments as exact domain site blocks.
- Verify the baseline through clean-bootstrap/rerun acceptance and VM E2E.
- Document the HTTP/HTTPS boundary and how to apply the new baseline to a VPS.

## Decisions

- The fallback is generic: it returns `Not Found` with HTTP status 404 and does
  not identify an Application or a prior visibility state.
- HTTP unmatched-host requests receive the fallback.
- HTTPS receives the fallback only after TLS succeeds. A TLS handshake failure
  is acceptable when Caddy has no usable certificate for that hostname.
- Pneuma does not manage DNS records, certificate retention, or Certificate
  Transparency history. Removing a public DNS record remains an operator action.
- The fallback belongs to the bootstrap-managed Caddy baseline, not to
  per-Application fragments or the `visibility set` use case.

## Non-goals

- Do not add DNS management, certificate management, wildcard certificates, or
  a generic HTTPS certificate solely for internalized hostnames.
- Do not alter Application, Deployment, RuntimeInstance, or Exposure persistence.
- Do not implement v0.4 reconciliation in this checkpoint.

## Acceptance Criteria

- The production and VM baselines validate with Caddy and include a generic HTTP
  404 fallback before importing managed Application fragments.
- Rerunning bootstrap applies the changed baseline atomically and remains
  idempotent once applied.
- A VM E2E scenario changes `redirect-public` from public to internal, confirms
  its runtime remains running, and receives HTTP 404 for the former hostname.
- Existing public Application routing continues to pass the HTTPS E2E assertion.
- Required shell and Rust CI gates pass; the disposable VM regressions record
  their actual result.
