# Requisitos da v0.1 do Pneuma

**Status:** Draft para validação na Iteração D0  
**Escopo relacionado:** [`v0.1-scope.md`](./v0.1-scope.md)  
**Convenção:** requisitos `MUST` são obrigatórios para `v0.1.0`; requisitos `SHOULD` podem ser adiados apenas com justificativa registrada.

## 1. Convenções

Cada requisito possui:

- **ID:** identificador estável;
- **Prioridade:** `MUST`, `SHOULD` ou `COULD`;
- **Verificação:** forma principal de comprovação;
- **Origem:** capacidade ou risco que motivou o requisito.

## 2. Requisitos funcionais

### Catálogo e manifesto

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| FR-001 | MUST | O Pneuma deve importar uma aplicação existente a partir de um repositório ou checkout suportado. | Teste de aceitação |
| FR-002 | MUST | O Pneuma deve localizar, carregar e validar um arquivo `pneuma.toml`. | Testes unitários e integração |
| FR-003 | MUST | O Pneuma deve rejeitar manifesto ausente, incompatível ou inválido com erro compreensível. | Testes negativos |
| FR-004 | MUST | O Pneuma deve persistir a aplicação e suas especificações. | Teste com SQLite real |
| FR-005 | MUST | Repetir a importação da mesma aplicação não deve criar registro duplicado. | Teste de idempotência |
| FR-006 | MUST | O usuário deve poder listar e consultar aplicações registradas. | CLI/TUI e teste de aceitação |
| FR-007 | SHOULD | O usuário deve poder remover uma aplicação somente após confirmação de que não existe operação em andamento. | Teste de integração |

### Source e revisão

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| FR-010 | MUST | O Pneuma deve resolver uma referência Git para um commit completo. | Teste com repositório temporário |
| FR-011 | MUST | Um deployment deve apontar para um commit imutável, nunca apenas para uma branch. | Inspeção do banco e teste |
| FR-012 | MUST | O Pneuma deve criar checkout isolado para cada revisão em build. | Teste de integração |
| FR-013 | MUST | Duas revisões devem poder ser preparadas sem alterar o conteúdo uma da outra. | Spike e teste |
| FR-014 | MUST | O Pneuma deve rejeitar revisão inexistente ou não pertencente ao repositório registrado. | Testes negativos |

### Build

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| FR-020 | MUST | O Pneuma deve construir uma imagem local a partir do `Containerfile` e contexto registrados. | Teste E2E |
| FR-021 | MUST | A imagem deve ser identificada de forma determinística pela aplicação e revisão. | Inspeção do runtime |
| FR-022 | MUST | Logs do build devem ser preservados ou acessíveis para diagnóstico. | Teste de falha |
| FR-023 | MUST | Falha ou cancelamento do build deve encerrar o deployment sem afetar a revisão ativa. | Teste de resiliência |
| FR-024 | SHOULD | Artefatos temporários de build devem ser removidos quando não forem necessários para diagnóstico ou rollback. | Teste de limpeza |

### Runtime

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| FR-030 | MUST | O Pneuma deve criar, iniciar, parar, reiniciar e remover uma instância de runtime. | Teste de integração Podman |
| FR-031 | MUST | O estado observado deve ser consultado no Podman/systemd e não inferido somente do banco. | Teste de divergência |
| FR-032 | MUST | Iniciar uma aplicação já iniciada não deve criar uma segunda instância `Current`. | Teste de idempotência |
| FR-033 | MUST | Parar uma aplicação já parada deve produzir sucesso idempotente ou resultado não destrutivo. | Teste de idempotência |
| FR-034 | MUST | A aplicação deve continuar executando após o encerramento da CLI ou TUI. | Teste manual/integração |
| FR-035 | MUST | A aplicação configurada para execução deve poder ser restaurada após reinicialização do host. | Spike e teste operacional |
| FR-036 | MUST | Cada instância deve possuir identificador externo, revisão, papel e endpoint local registrados. | Inspeção do banco |
| FR-037 | MUST | Somente uma instância por aplicação pode possuir papel `Current`. | Constraint e teste |
| FR-038 | SHOULD | O Pneuma deve detectar runtime registrado que deixou de existir. | Teste de reconciliação sob demanda |
| FR-039 | SHOULD | O Pneuma deve detectar runtime gerenciado existente sem registro correspondente. | `doctor` e teste |

### Deployment

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| FR-040 | MUST | Cada tentativa de implantação deve criar um `Deployment` persistido. | Teste de integração |
| FR-041 | MUST | O deployment deve registrar aplicação, revisão, estado, horários e resultado. | Inspeção do banco |
| FR-042 | MUST | O Pneuma deve criar a nova revisão como candidata antes de substituir a atual. | Teste E2E |
| FR-043 | MUST | A candidata não deve receber tráfego público antes da verificação interna. | Teste de rota |
| FR-044 | MUST | Um deployment só pode ser marcado como bem-sucedido após ativação e verificações obrigatórias. | Teste de estados |
| FR-045 | MUST | Falha da candidata deve preservar a revisão atual saudável. | Teste de falha |
| FR-046 | MUST | O usuário deve poder listar o histórico de deployments. | CLI/TUI |
| FR-047 | MUST | O usuário deve poder solicitar rollback para o último deployment saudável elegível. | Teste E2E |
| FR-048 | MUST | O rollback deve ser registrado como nova operação auditável. | Inspeção do histórico |
| FR-049 | MUST | O Pneuma deve impedir dois deployments simultâneos para a mesma aplicação. | Teste concorrente |
| FR-050 | MUST | Ao iniciar, o Pneuma deve identificar deployments interrompidos e classificá-los para retomada segura ou falha recuperável. | Teste de crash recovery |

### Health check

|---|---:|---|---|
| FR-060 | MUST | A aplicação deve declarar caminho e status HTTP esperado. | Validação do manifesto |

| FR-062 | MUST | O resultado deve registrar sucesso ou causa estruturada de falha. | Inspeção do histórico |
| FR-063 | MUST | O Pneuma deve executar health check interno da candidata antes da ativação. | Teste E2E |
| FR-064 | MUST | Para aplicação pública, o Pneuma deve verificar o endpoint externo após a troca. | Teste E2E |
| FR-065 | MUST | Falha no health check externo deve restaurar a rota anterior quando possível. | Teste de rollback |
| FR-066 | SHOULD | O histórico deve registrar tentativas suficientes para diagnóstico sem armazenar dados sensíveis. | Revisão de logs |

|---|---:|---|---|
| FR-070 | MUST | O usuário deve poder alternar a aplicação entre `Internal` e `Public`. | CLI/TUI |

| FR-072 | MUST | Uma aplicação pública deve possuir domínio válido e permitido. | Validação |
| FR-073 | MUST | O Pneuma deve gerar configuração do Caddy em área controlada. | Teste de integração |

| FR-075 | MUST | A substituição do arquivo deve ser atômica. | Teste de filesystem |

### Interfaces

## 3. Requisitos não funcionais

### Confiabilidade e consistência

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| NFR-001 | MUST | Operações mutáveis devem ser idempotentes quando repetidas com os mesmos parâmetros. | Testes |
| NFR-002 | MUST | Estado persistido e efeitos externos devem ser coordenados como processo recuperável, sem assumir transação ACID distribuída. | Revisão e crash tests |
| NFR-003 | MUST | O banco nunca deve ser a única fonte do estado observado do runtime. | Teste de divergência |
| NFR-004 | MUST | Uma falha do Pneuma não deve encerrar uma aplicação saudável já supervisionada. | Teste operacional |
| NFR-005 | MUST | Uma revisão inválida não deve substituir a revisão saudável. | Teste E2E |
| NFR-006 | MUST | A atualização do Caddy deve preservar a configuração anterior até que a nova seja validada. | Teste |
| NFR-007 | MUST | Toda operação interrompida deve possuir estado suficiente para diagnóstico e recuperação determinística. | Crash tests |
| NFR-008 | SHOULD | O sistema deve tolerar reinício do processo entre etapas sem criar recursos duplicados. | Testes de injeção de falha |

### Segurança

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| NFR-010 | MUST | Containers devem executar rootless e sem modo privilegiado. | Inspeção |
| NFR-011 | MUST | O manifesto não pode solicitar mounts arbitrários do host na v0.1. | Validação |
| NFR-012 | MUST | Processos externos devem ser executados por argumentos estruturados, sem concatenar comandos para shell. | Revisão de código |
| NFR-013 | MUST | Nomes e caminhos derivados da aplicação devem ser normalizados e confinados a diretórios controlados. | Testes de segurança |
| NFR-014 | MUST | A configuração do Caddy gerada pelo Pneuma deve ficar em diretório dedicado. | Inspeção |
| NFR-015 | MUST | O usuário do Pneuma deve possuir somente as permissões necessárias. | Revisão de permissões |
| NFR-016 | MUST | Logs não devem registrar secrets ou credenciais. | Testes/revisão |
| NFR-017 | MUST | Domínios públicos devem ser validados contra política configurada. | Testes |
| NFR-018 | MUST | Checkouts devem tratar symlinks e paths de forma a impedir escrita fora da área controlada. | Testes adversariais |
| NFR-019 | SHOULD | Falhas de segurança relevantes devem possuir código de erro identificável. | Revisão de erros |

### Manutenibilidade

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| NFR-020 | MUST | O domínio e os casos de uso não devem depender de bibliotecas de CLI, TUI, SQLite, Git, Podman ou Caddy. | Teste de dependências |
| NFR-021 | MUST | Adapters devem implementar ports definidos pelas necessidades dos casos de uso. | Revisão arquitetural |
| NFR-022 | MUST | A arquitetura deve permanecer um monólito modular na v0.1. | Revisão |
| NFR-023 | MUST | Novas migrations não devem alterar migrations já publicadas. | CI |
| NFR-024 | MUST | Casos de uso críticos devem possuir testes com fakes e testes de integração dos adapters. | Cobertura por comportamento |
| NFR-025 | SHOULD | Limites lógicos não precisam virar crates separados sem necessidade demonstrada. | Revisão de estrutura |
| NFR-026 | SHOULD | Documentos devem refletir a arquitetura implementada, não somente a arquitetura pretendida. | Checkpoint de arquitetura |

### Observabilidade e diagnóstico

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| NFR-030 | MUST | Operações devem produzir logs estruturados com IDs de aplicação, deployment e operação. | Inspeção |
| NFR-031 | MUST | Erros devem preservar contexto e causa sem expor dados sensíveis. | Testes |
| NFR-032 | MUST | O histórico deve permitir reconstruir o resultado de cada deployment. | Teste |
| NFR-033 | SHOULD | Duração de build, start, health check e deployment deve ser registrada. | Inspeção |
| NFR-034 | SHOULD | O diagnóstico deve diferenciar estado desejado, persistido, observado e materializado. | `doctor` |

### Desempenho e capacidade

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| NFR-040 | SHOULD | Consultas locais de listagem e status devem responder em até 2 segundos em condições normais da VPS. | Medição |
| NFR-041 | MUST | O sistema deve suportar o site piloto e múltiplas aplicações simples no mesmo host sem arquitetura distribuída. | Teste de capacidade básico |
| NFR-042 | MUST | Operações longas não devem bloquear permanentemente a interface sem atualização de estado. | Teste |
| NFR-043 | COULD | O build pode limitar concorrência para proteger recursos da VPS. | Configuração futura |

### Portabilidade e ambiente

| ID | Prioridade | Requisito | Verificação |
|---|---:|---|---|
| NFR-050 | MUST | A v0.1 deve funcionar no Linux alvo com systemd, Podman rootless, Git, Caddy e SQLite. | Instalação limpa |
| NFR-051 | MUST | Paths de dados e configuração devem ser configuráveis ou derivados de convenção documentada. | Teste |
| NFR-052 | SHOULD | Testes de domínio e casos de uso devem rodar sem Podman ou Caddy instalados. | CI |
| NFR-053 | SHOULD | Testes de integração devem poder usar ambiente descartável. | Pipeline local/CI |

## 4. Restrições

| ID | Restrição |
|---|---|
| CON-001 | Um único host será administrado na v0.1. |
| CON-002 | Uma aplicação corresponde a um único container HTTP. |
| CON-003 | O build de produção ocorre localmente na VPS. |
| CON-004 | A unidade de deployment é um commit Git. |
| CON-005 | O estado persistente utiliza SQLite. |
| CON-006 | O runtime utiliza Podman rootless e supervisão do systemd/Quadlet, sujeita à validação do spike. |
| CON-007 | A exposição utiliza Caddy. |
| CON-008 | Não haverá daemon obrigatório ou API remota na v0.1. |
| CON-009 | Não haverá suporte a configuração privilegiada, mounts arbitrários ou acesso ao socket do Podman pela aplicação. |
| CON-010 | O domínio principal só será migrado após validação em domínio temporário. |

## 5. Hipóteses

| ID | Hipótese | Como validar |
|---|---|---|
| ASM-001 | CLI e TUI podem executar o Core diretamente sem conflitos inaceitáveis. | Spike de locking e testes concorrentes |
| ASM-002 | Quadlet/systemd user units mantêm containers rootless após logout e reboot. | Spike Podman |
| ASM-003 | O usuário do Pneuma consegue administrar arquivos de rota sem acesso root amplo. | Spike Caddy/permissões |
| ASM-004 | Portas locais distintas permitem coexistência de `Current` e `Candidate`. | Spike rollback |
| ASM-005 | O site pode responder a um health check HTTP representativo em `/`. | Validação do site |
| ASM-006 | SQLite é suficiente para volume e concorrência da v0.1. | Teste concorrente |
| ASM-007 | O fluxo anterior do site pode ser restaurado independentemente do Pneuma. | Ensaio de reversão |

## 6. Questões abertas da D0

| ID | Questão | Decisão necessária antes de |
|---|---|---|
| OQ-001 | A supervisão será feita por Quadlet user units ou por containers Podman com política de restart? | Implementação de Runtime |
| OQ-002 | Qual mecanismo de lock será usado: lock de arquivo, transação SQLite ou combinação? | Primeiro caso de uso mutável |
| OQ-003 | Qual intervalo de portas loopback será reservado às instâncias? | Deployment candidato |
| OQ-004 | Como o usuário rootless atualizará a configuração consumida pelo Caddy com privilégio mínimo? | Adapter Caddy |
| OQ-005 | O repositório remoto será clonado por HTTPS, SSH ou ambos na v0.1? | Importação remota |
| OQ-006 | Quais estados interrompidos podem ser retomados e quais devem terminar como `Failed`? | Recovery |
| OQ-007 | O backup será exposto por comando do Pneuma ou somente por runbook na v0.1? | Hardening |
| OQ-008 | Por quanto tempo imagens, checkouts e runtimes anteriores serão retidos? | Política de retenção |
