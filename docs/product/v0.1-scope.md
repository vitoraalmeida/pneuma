# Escopo da v0.1 do Pneuma

**Status:** Draft para validação na Iteração D0  
**Release-alvo:** `v0.1.0`  
**Aplicação-piloto:** `vitoralmeida.tech`  
**Ambiente-alvo:** uma única VPS Linux administrada pelo usuário

## 1. Propósito

A v0.1 deve provar que o Pneuma consegue assumir a operação de uma aplicação containerizada existente de maneira reproduzível, observável e recuperável.

A aplicação-piloto será o site pessoal `vitoralmeida.tech`. O site já existirá como repositório Git compatível com o contrato mínimo do Pneuma, contendo um `Containerfile` e um `pneuma.toml`.

O compromisso central da release é:

> Importar o site pessoal, implantar uma revisão Git específica, verificar sua saúde, administrar seu ciclo de execução e controlar sua exposição pública pelo Caddy.

A v0.1 não tenta criar uma plataforma genérica completa. Ela valida os fundamentos que serão reutilizados nas versões seguintes.

## 2. Problema

Atualmente, a operação do site depende de comandos e conhecimento mantidos fora de um sistema explícito. Isso dificulta responder de forma confiável:

- qual revisão está em execução;
- como iniciar ou parar a aplicação;
- se o container realmente está saudável;
- como implantar uma nova revisão;
- como impedir que uma revisão inválida substitua a anterior;
- como remover a exposição pública sem parar a aplicação;
- como recuperar o estado depois de uma falha ou reinicialização.

O Pneuma deve transformar esse processo em um fluxo controlado e auditável.

## 3. Usuário da v0.1

A v0.1 terá um único perfil de usuário:

**Operador e desenvolvedor do servidor**

Esse usuário:

- possui acesso SSH à VPS;
- administra o repositório da aplicação;
- utiliza a CLI ou TUI do Pneuma;
- decide quando importar, implantar, iniciar, parar ou alterar a exposição;
- pode executar procedimentos de contingência fora do Pneuma.

Não haverá modelo multiusuário, RBAC ou autenticação própria na v0.1.

## 4. Resultado esperado

Ao final da v0.1:

1. o site estará registrado no catálogo do Pneuma;
2. uma revisão Git imutável estará associada a cada deployment;
3. o Pneuma conseguirá construir a imagem na VPS;
4. a aplicação será executada de forma rootless;
5. o estado observado será consultado no runtime real;
6. uma revisão candidata só será ativada após health check;
7. uma falha de deployment não substituirá a versão saudável;
8. o Caddy será configurado pelo Pneuma para exposição pública ou interna;
9. CLI e TUI utilizarão os mesmos casos de uso;
10. aplicações continuarão executando quando CLI ou TUI forem encerradas;
11. o catálogo e o histórico sobreviverão à reinicialização do Pneuma;
12. a adoção do domínio principal possuirá um procedimento de reversão independente do Pneuma.

## 5. Jornada principal

```text
Preparar aplicação compatível
    ↓
Importar repositório
    ↓
Validar pneuma.toml
    ↓
Registrar aplicação
    ↓
Resolver revisão Git
    ↓
Construir imagem
    ↓
Criar runtime candidato
    ↓
Executar health check interno
    ↓
Ativar revisão
    ↓
Configurar exposição pelo Caddy
    ↓
Verificar endpoint público
    ↓
Consultar estado e histórico
```

## 6. Capacidades incluídas

### 6.1 Catálogo e importação

- importar uma aplicação containerizada existente;
- aceitar repositório local ou URL Git suportada pelo adapter;
- localizar e validar `pneuma.toml`;
- persistir identidade e especificações da aplicação;
- impedir registros duplicados;
- listar e consultar aplicações registradas.

### 6.2 Revisões e build

- resolver uma referência Git para um commit;
- tratar o commit como revisão imutável;
- criar checkout isolado da revisão;
- construir imagem local com Podman;
- identificar a imagem pelo nome da aplicação e commit;
- registrar logs e resultado do build.

### 6.3 Runtime

- criar uma instância de runtime;
- iniciar, parar, reiniciar e inspecionar a aplicação;
- consultar estado observado diretamente no Podman/systemd;
- manter no máximo uma instância com papel `Current`;
- manter uma candidata separada durante o deployment;
- preservar a execução independentemente da CLI ou TUI.

### 6.4 Deployment e rollback

- registrar uma tentativa de deployment;
- executar uma máquina de estados persistida;
- iniciar a revisão candidata em endpoint local separado;
- verificar a candidata antes de ativá-la;
- manter referência à revisão anterior;
- rejeitar ou remover a candidata quando ela falhar;
- realizar rollback manual para o último deployment saudável;
- manter histórico de deployments e causas de falha.

### 6.5 Health check

- configurar caminho, status HTTP esperado, timeout e tentativas;
- executar verificação interna da candidata;
- verificar o endpoint público depois da troca de rota;
- registrar resultado estruturado;
- diferenciar “processo iniciado” de “deployment bem-sucedido”.

### 6.6 Exposição

- manter a aplicação interna ou pública;
- configurar domínio público;
- gerar configuração do Caddy de forma determinística;
- validar a configuração antes de aplicá-la;
- substituir a configuração de forma atômica;
- remover a rota pública sem parar a aplicação;
- restaurar a configuração anterior quando a ativação falhar.

### 6.7 Interfaces

A CLI deve oferecer, no mínimo:

```text
pneuma app import
pneuma app list
pneuma app status
pneuma app deploy
pneuma app start
pneuma app stop
pneuma app expose
pneuma deployment list
pneuma deployment rollback
pneuma doctor
pneuma version
```

A TUI deve permitir executar as operações principais sem possuir lógica direta de Git, Podman, SQLite ou Caddy.

### 6.8 Operação do Pneuma

- instalação documentada;
- usuário e diretórios dedicados;
- migrations de banco;
- backup e restauração documentados do SQLite;
- diagnóstico básico do ambiente;
- atualização e rollback do binário documentados;
- logs estruturados suficientes para diagnóstico;
- procedimento de contingência que não dependa do próprio Pneuma.

### 6.9 Adoção do site

- validar o fluxo em ambiente local ou VM;
- validar na VPS usando domínio temporário;
- manter o site atual ativo durante o ensaio;
- trocar o domínio principal somente depois da validação;
- manter plano testado para restaurar o fluxo anterior.

## 7. Critérios finais de aceite

A release estará concluída quando, em uma instalação limpa e seguindo apenas a documentação, for possível demonstrar:

1. importar o repositório do site;
2. importar novamente sem criar duplicidade;
3. implantar um commit específico;
4. acessar a aplicação por endpoint interno;
5. tornar a aplicação pública em domínio temporário;
6. consultar o estado real do runtime;
7. parar e iniciar a aplicação;
8. implantar uma segunda revisão saudável;
9. tentar implantar uma revisão cujo health check falha;
10. confirmar que a versão saudável continua disponível;
11. executar rollback manual para a revisão anterior;
12. tornar a aplicação interna sem pará-la;
13. reiniciar CLI/TUI sem interromper a aplicação;
14. reiniciar o Pneuma e reconstruir o estado observado;
15. executar diagnóstico básico;
16. realizar backup e restauração de teste do banco;
17. migrar `vitoralmeida.tech` para o fluxo do Pneuma;
18. restaurar o fluxo anterior sem depender do Pneuma;
19. executar o cenário de aceitação automatizado ou semiautomatizado;
20. consultar histórico com revisão, estado, horário e causa de falha.

## 8. Não objetivos

Não fazem parte da v0.1:

- criação de novos repositórios ou projetos por template;
- build no GitHub Actions;
- GHCR ou outro registry remoto;
- deployment por digest OCI;
- deploy automático após merge;
- webhooks ou API pública;
- daemon obrigatório ou control plane remoto;
- múltiplos servidores;
- alta disponibilidade do Pneuma;
- Kubernetes;
- múltiplos serviços dentro da mesma aplicação;
- criação declarativa de redes entre aplicações;
- volumes arbitrários definidos pelo projeto;
- gestão completa de secrets;
- autenticação entre serviços;
- autenticação própria, RBAC ou múltiplos usuários;
- assinatura de imagens;
- SBOM ou provenance;
- canary ou rollout gradual;
- autoscaling;
- interface web;
- observabilidade centralizada.

Essas capacidades poderão ser introduzidas somente após a validação dos fundamentos da v0.1.

## 9. Restrições

- o host será Linux com systemd;
- a execução será baseada em Podman rootless;
- a exposição pública será feita por Caddy;
- o estado persistente será armazenado em SQLite;
- a unidade implantável será um commit Git;
- o build ocorrerá na VPS;
- o sistema operará em um único host;
- a aplicação-piloto terá um único container e uma única porta HTTP;
- o domínio principal não será o primeiro ambiente de validação;
- a configuração do projeto não poderá solicitar modo privilegiado ou mounts arbitrários do host.

## 10. Hipóteses da D0

As hipóteses abaixo devem ser confirmadas pelos spikes:

- Quadlet/systemd user units são suficientes para supervisionar os runtimes rootless;
- o Caddy pode consumir arquivos por aplicação com validação e reload seguro;
- o usuário do Pneuma pode atualizar somente o diretório de configuração necessário;
- duas revisões podem coexistir em portas locais diferentes durante um deployment;
- o estado persistido permite retomar ou encerrar operações interrompidas;
- CLI e TUI podem executar o Core diretamente sem daemon na v0.1;
- um mecanismo de lock local é suficiente para impedir operações concorrentes conflitantes.

## 11. Indicadores de sucesso

A v0.1 é bem-sucedida quando:

- o site principal é operado pelo Pneuma por período estável;
- nenhum deployment inválido substitui uma revisão saudável;
- todas as operações importantes deixam estado e logs diagnosticáveis;
- o procedimento de reversão foi ensaiado;
- uma pessoa consegue compreender o fluxo pelo repositório e pela demonstração;
- o projeto possui base suficiente para substituir build local por release OCI na v0.2.

## 12. Evidências da release

A release deverá preservar:

- diagrama de arquitetura atualizado;
- ADRs relevantes;
- script de aceitação;
- logs de um deployment bem-sucedido;
- logs de um deployment rejeitado;
- demonstração de alteração de exposição;
- demonstração de recuperação;
- release notes;
- limitações conhecidas;
- vídeo curto do fluxo completo.
