# Escopo e requisitos da v0.1 do Pneuma

**Status:** documento vivo — contrato da release `v0.1.0`
**Aplicação-piloto:** `vitoralmeida.tech`
**Ambiente-alvo:** uma única VPS Linux administrada pelo usuário

Consolida os antigos `v0.1-scope.md` e `v0.1-requirements.md` da Iteração D0.
Como a v0.1 é entregue em incrementos, o estado real da implementação está no
código e em
[`docs/iterations/current-iteration.md`](../iterations/current-iteration.md);
este documento define o alvo, não o progresso.

## 1. Propósito

A v0.1 deve provar que o Pneuma consegue assumir a operação de uma aplicação
containerizada existente de maneira reproduzível, observável e recuperável.

> Importar o site pessoal, implantar uma revisão Git específica, verificar sua
> saúde, administrar seu ciclo de execução e controlar sua exposição pública
> pelo Caddy.

A v0.1 não tenta criar uma plataforma genérica completa; ela valida os
fundamentos reutilizados nas versões seguintes.

## 2. Problema

A operação do site hoje depende de comandos e conhecimento fora de um sistema
explícito: não há resposta confiável para qual revisão está em execução, se o
container está saudável, como implantar sem derrubar a versão boa ou como
recuperar o estado após falha. O Pneuma transforma esse processo em um fluxo
controlado e auditável.

## 3. Usuário

Um único perfil: o **operador e desenvolvedor do servidor**, com acesso SSH à
VPS e ao repositório da aplicação. Sem multiusuário, RBAC ou autenticação
própria na v0.1.

## 4. Jornada principal

O GitHub Actions valida cada revisão, mas não acessa a VPS. O CI publica a
imagem em um registry (ex.: GHCR) com digest imutável; o operador solicita o
deployment dessa imagem na VPS, ou usa o caminho alternativo de build local a
partir do checkout Git.

```text
Preparar aplicação compatível → Importar repositório (manifesto v2)
    → Registrar aplicação (spec + delivery) → app deploy --image <repo@sha256:...>
    → Pull + verificação de digest → Criar Release → Runtime candidato
    → Health check interno → Ativar → Configurar exposição pelo Caddy
    → Verificar endpoint público → Consultar estado e histórico
```

O caminho alternativo `app deploy-source <app> <repo> --revision <rev>` constrói
a imagem localmente a partir do commit resolvido e segue o mesmo engine de
deployment a partir da Release.

## 5. Capacidades incluídas

### 5.1 Catálogo e importação

- importar uma aplicação containerizada existente (repositório local ou URL Git);
- localizar, carregar e validar `pneuma.toml` (schema v2), rejeitando manifesto
  ausente ou inválido com erro compreensível;
- exigir seção `[delivery]` (`type = "oci"`, `image = <repositório permitido>`);
  `[source]`/`[build]` opcionais apenas para `deploy-source`;
- persistir identidade, especificações e entrega (`application_delivery_specs`)
  da aplicação;
- importação idempotente, sem registros duplicados;
- listar e consultar aplicações registradas.

### 5.2 Revisões, build e entrega OCI

- o caminho oficial implanta uma imagem OCI imutável (`app deploy --image
  <repo@sha256:...>`): pull no Podman, inspeção do digest e confirmação de que o
  digest corresponde ao solicitado;
- rejeitar tags mutáveis e imagens de repositório diferente do declarado em
  `[delivery]`;
- o caminho alternativo `deploy-source` resolve uma referência Git para um
  commit completo e imutável — deployment nunca aponta apenas para uma branch;
- rejeitar revisão inexistente ou não pertencente ao repositório registrado;
- criar checkout isolado por revisão, sem interferência entre revisões;
- construir a imagem local com Podman, identificada deterministicamente por
  aplicação e commit;
- falha ou cancelamento do build encerra o deployment sem afetar a revisão
  ativa;
- logs e resultado do build acessíveis para diagnóstico.

### 5.3 Runtime

- criar, iniciar, parar, reiniciar, inspecionar e remover instâncias;
- consultar o estado observado no Podman, não apenas no banco;
- no máximo uma instância `Current` por aplicação, garantido por constraint;
- candidata separada durante o deployment, inalcançável publicamente;
- start/stop idempotentes;
- aplicação continua executando quando a CLI termina.

### 5.4 Deployment e rollback

- registrar cada tentativa como `Deployment` persistido, com estado, horários e
  resultado;
- impedir dois deployments simultâneos para a mesma aplicação;
- verificar a candidata antes de ativá-la; ela nunca recebe tráfego antes do
  health check interno;
- falha da candidata preserva a revisão saudável atual;
- rollback manual para o último deployment saudável, registrado de forma
  auditável;
- histórico de deployments com causas de falha.

### 5.5 Health check

- caminho, status HTTP esperado, timeout, intervalo e tentativas configuráveis;
- verificação interna da candidata antes da ativação;
- verificação do endpoint público após a troca de rota;
- resultado estruturado, diferenciando “processo iniciado” de “deployment
  bem-sucedido”.

### 5.6 Exposição

- visibilidade interna ou pública; tornar interna não para a aplicação;
- aplicação pública exige domínio válido;
- configuração do Caddy gerada deterministicamente em área dedicada, validada
  antes de aplicar e substituída de forma atômica;
- a configuração anterior é preservada até a nova ser validada e verificada;
- falha na ativação restaura a configuração anterior;
- estado desejado de exposição persistido separadamente da materialização.

### 5.7 Interfaces

CLI mínima:

```text
pneuma app import
pneuma app list
pneuma app status
pneuma app deploy
pneuma app start
pneuma app stop
pneuma app expose
pneuma deployment list
pneuma deployment rollback
pneuma doctor
pneuma version
```

A TUI executa as operações principais pelos mesmos casos de uso da CLI, sem
chamar Git, Podman, SQLite ou Caddy diretamente. Operações longas apresentam
progresso; erros retornam código de saída e mensagem adequados.

### 5.8 Operação do Pneuma

- instalação documentada, com usuário e diretórios dedicados;
- migrations controladas e imutáveis após publicação;
- backup e restauração do SQLite documentados e ensaiados;
- diagnóstico básico do ambiente (`doctor`);
- atualização e reversão do binário documentadas;
- logs suficientes para diagnóstico, sem secrets;
- contingência do site principal independente do Pneuma.

### 5.9 Adoção do site

- validar o fluxo em ambiente local ou VM, depois na VPS com domínio
  temporário, mantendo o site atual ativo durante o ensaio;
- trocar o domínio principal somente depois da validação;
- manter plano testado para restaurar o fluxo anterior.

## 6. Requisitos transversais

- operações mutáveis idempotentes quando repetidas com os mesmos parâmetros;
- nenhuma transação distribuída assumida: estado persistido e efeitos externos
  coordenados como saga recuperável;
- uma falha do Pneuma não encerra uma aplicação saudável;
- containers rootless, sem modo privilegiado, mounts arbitrários ou socket do
  Podman;
- processos externos executados com argumentos estruturados, sem shell;
- nomes e caminhos derivados da aplicação normalizados e confinados a diretórios
  controlados; symlinks que escapam da raiz são rejeitados;
- paths de dados e configuração configuráveis por variáveis de ambiente;
- testes de casos de uso rodam sem Podman ou Caddy instalados; testes de
  integração usam ambiente descartável.

## 7. Critérios finais de aceite

A release estará concluída quando, em uma instalação limpa e seguindo apenas a
documentação, for possível demonstrar:

1. importar o repositório do site;
2. importar novamente sem criar duplicidade;
3. implantar um commit específico;
4. acessar a aplicação por endpoint interno;
5. tornar a aplicação pública em domínio temporário;
6. consultar o estado real do runtime;
7. parar e iniciar a aplicação;
8. implantar uma segunda revisão saudável;
9. tentar implantar uma revisão cujo health check falha;
10. confirmar que a versão saudável continua disponível;
11. executar rollback manual para a revisão anterior;
12. tornar a aplicação interna sem pará-la;
13. reiniciar CLI/TUI sem interromper a aplicação;
14. reiniciar o Pneuma e reconstruir o estado observado;
15. executar diagnóstico básico;
16. realizar backup e restauração de teste do banco;
17. migrar `vitoralmeida.tech` para o fluxo do Pneuma;
18. restaurar o fluxo anterior sem depender do Pneuma;
19. executar o cenário de aceitação automatizado ou semiautomatizado;
20. consultar histórico com revisão, estado, horário e causa de falha.

## 8. Não objetivos

Não fazem parte da v0.1:

- criação de repositórios ou projetos por template;
- build no GitHub Actions como caminho obrigatório; deploy automático após merge;
  webhooks ou API pública;
- daemon obrigatório ou control plane remoto;
- múltiplos servidores ou alta disponibilidade;
- Kubernetes; múltiplos serviços por aplicação;
- volumes arbitrários definidos pelo projeto;
- gestão completa de secrets; autenticação entre serviços;
- autenticação própria, RBAC ou múltiplos usuários;
- assinatura de imagens, SBOM ou provenance;
- canary, rollout gradual ou autoscaling;
- interface web; observabilidade centralizada.

## 9. Restrições

- um único host Linux com systemd;
- runtime em Podman rootless; exposição por Caddy; estado em SQLite;
- a unidade implantável é uma Release imutável identificada por digest OCI,
  vinda de registry (caminho oficial) ou de build local (`deploy-source`);
- a aplicação-piloto tem um único container e uma única porta HTTP;
- o domínio principal só é migrado após validação em domínio temporário;
- o projeto não pode solicitar modo privilegiado ou mounts arbitrários do host.

## 10. Questões em aberto

- política de retenção de imagens, checkouts e runtimes anteriores;
- backup exposto como comando do Pneuma ou apenas como runbook.
